# Анализ предметной области

## 1. Описание системы

**AviaBooking** — информационная система учёта рейсов и бронирования билетов
авиакомпании. Система позволяет:

- Гостям — искать рейсы и просматривать расписание
- Зарегистрированным пользователям — бронировать билеты, управлять своими бронями
- Администраторам — управлять рейсами, самолётами, аэропортами

**Тип системы:** Web-приложение (REST API + веб-интерфейс)
**Аналог:** Aviasales (упрощённая версия для одной авиакомпании)

---

## 2. Границы проекта

### 2.1. В scope (что делаем)

- Поиск рейсов (one-way, в одну сторону)
- Регистрация и аутентификация пользователей (JWT)
- Бронирование билетов
- Просмотр и отмена своих броней
- Управление рейсами (CRUD) для администратора
- Управление справочниками: аэропорты, самолёты, авиакомпании, страны, города
- Валидация ввода и обработка исключений
- Логирование действий (Serilog)
- Юнит-тесты для критичной логики

### 2.2. Вне scope (что НЕ делаем)

- Поиск туда-обратно (round-trip)
- Выбор места на 2D-карте салона самолёта
- Перенос брони на другой рейс (reissue)
- Реальная оплата (интеграция с платёжным шлюзом)
- Email/SMS-уведомления
- Мультиавиакомпанийность (агрегатор, как Aviasales)
- Программы лояльности (бонусные мили)
- Возврат средств (refund) с реальной транзакцией

## 3. Акторы системы

| Актор | Описание | Аутентификация |
|-------|----------|----------------|
| **Гость** | Неавторизованный пользователь. Может искать рейсы, но не может бронировать | Нет |
| **User** | Зарегистрированный пользователь. Может бронировать, управлять своими бронями | JWT |
| **Admin** | Администратор системы. Управляет рейсами и справочниками | JWT + роль |

**Важно:** гость — это не сущность в базе данных, а состояние пользователя
(отсутствие токена). В таблице `Users` хранятся только User и Admin.

### 4.3. Связи между сущностями
Country 1──N City 1──N Airport
Country 1──N Airline 1──N Aircraft
Airline 1──N Flight
Aircraft 1──N Flight
Airport 1──N Flight (×2: DepartureAirport, ArrivalAirport)
Flight 1──N Ticket
FareClass 1──N Ticket
User 1──N Booking 1──N Ticket


**Особые случаи:**

1. **Flight ↔ Airport — две связи 1:N.**
   У рейса два аэропорта (вылета и прилёта). В БД это две колонки внешних ключей:
   `DepartureAirportId` и `ArrivalAirportId`, обе ссылаются на `Airports.Id`.
   Требует явной настройки в EF Core (OnModelCreating).

2. **Booking ↔ Ticket — 1:N.**
   Одно бронирование может содержать несколько билетов
   (например, для семьи или в перспективе — туда-обратно).

3. **Ticket.Price — фиксируется при покупке.**
   Даже если потом изменят `Flight.BasePrice` или `FareClass.Multiplier`,
   цена уже купленного билета не меняется.

## 5. Пользовательские сценарии (UML Use Case)

### Сценарий 1: Поиск рейса

**Актор:** Гость
**Предусловие:** нет
**Основной поток:**
1. Гость открывает главную страницу
2. Вводит параметры поиска: откуда, куда, дата вылета, количество пассажиров, класс
3. Нажимает кнопку «Найти»
4. Система возвращает список подходящих рейсов, отсортированных по времени вылета
5. Гость может применить фильтры (авиакомпания, диапазон цен) и сортировку (по цене, времени, длительности)
6. Гость нажимает на рейс — открывается страница с деталями

**Постусловие:** состояние системы не изменилось
**Альтернативные потоки:**
- Если рейсов не найдено → показать сообщение «Ничего не найдено»
- Если дата вылета в прошлом → ошибка валидации
- Если аэропорт вылета = аэропорт прилёта → ошибка валидации

---

### Сценарий 2: Регистрация

**Актор:** Гость
**Предусловие:** гость не авторизован
**Основной поток:**
1. Гость нажимает «Регистрация»
2. Заполняет форму: email, пароль, имя, фамилия
3. Нажимает «Зарегистрироваться»
4. Система проверяет уникальность email
5. Хеширует пароль (BCrypt)
6. Создаёт запись в `Users` с ролью `User`
7. Возвращает JWT-токен
8. Гость становится авторизованным пользователем

**Постусловие:** в БД создан новый User, клиент получил токен
**Альтернативные потоки:**
- Если email уже занят → ошибка «Email уже используется»
- Если пароль слабый (< 6 символов) → ошибка валидации
- Если email некорректен → ошибка валидации

---

### Сценарий 3: Вход

**Актор:** Гость
**Предусловие:** есть зарегистрированный аккаунт
**Основной поток:**
1. Гость нажимает «Вход»
2. Вводит email и пароль
3. Система находит пользователя по email
4. Проверяет хеш пароля (BCrypt.Verify)
5. Возвращает JWT-токен
6. Гость становится авторизованным

**Постусловие:** клиент получил токен
**Альтернативные потоки:**
- Если email не найден или пароль неверный → ошибка «Неверные учётные данные»
  (специально не уточняем, что именно неверно — стандарт безопасности)

---

### Сценарий 4: Покупка билета

**Актор:** Гость → User (после входа/регистрации)
**Предусловие:** рейс найден и выбран
**Основной поток:**
1. Гость нажимает «Купить» на странице рейса
2. Если не авторизован → редирект на форму входа/регистрации
3. После авторизации → форма ввода пассажиров (ФИО, паспорт)
4. Выбор класса обслуживания (Economy / Business)
5. Система рассчитывает цену: `Flight.BasePrice × FareClass.Multiplier`
6. Пользователь нажимает «Забронировать»
7. Система создаёт `Booking` со статусом `Pending` и связанные `Ticket`-ы
8. Пользователь нажимает «Оплатить» (заглушка)
9. `Booking` переходит в статус `Confirmed`

**Постусловие:** создан Booking с Ticket-ами, статус Confirmed
**Альтернативные потоки:**
- Если свободных мест на рейсе не хватает → ошибка «Недостаточно мест»
- Если пользователь закрыл форму оплаты → Booking остаётся Pending

---

### Сценарий 5: Просмотр своих броней

**Актор:** User
**Предусловие:** авторизован
**Основной поток:**
1. Пользователь открывает личный кабинет
2. Система возвращает список его Booking-ов (с пагинацией)
3. Пользователь нажимает на Booking → видит детали (рейс, пассажиры, цена, статус)

**Постусловие:** состояние системы не изменилось

---

### Сценарий 6: Отмена брони

**Актор:** User
**Предусловие:** Booking существует, статус не Cancelled, рейс ещё не вылетел
**Основной поток:**
1. Пользователь открывает свой Booking
2. Нажимает «Отменить»
3. Система меняет статус `Booking.Status` на `Cancelled`
4. Все Ticket-ы в этой брони освобождают места на рейсе

**Постусловие:** Booking.Status = Cancelled
**Альтернативные потоки:**
- Если рейс уже вылетел (`DepartureTime < now`) → ошибка «Отмена невозможна»

---

### Сценарий 7: Управление рейсами

**Актор:** Admin
**Предусловие:** авторизован с ролью Admin
**Основной поток:**
1. Admin открывает админ-панель
2. Просматривает список рейсов
3. Может выполнить действия:
   - **Создать рейс:** форма (номер, авиакомпания, самолёт, аэропорты, время, базовая цена)
   - **Изменить рейс:** перенести время, изменить цену
   - **Отменить рейс:** установить статус `Cancelled` (не удалять!)
4. Изменения сохраняются в БД

**Постусловие:** данные рейсов изменены
**Альтернативные потоки:**
- Если `DepartureTime >= ArrivalTime` → ошибка валидации
- Если `DepartureAirportId == ArrivalAirportId` → ошибка валидации
- Если на рейс уже проданы билеты и admin пытается «удалить» → предлагается отмена

## 6. Паттерны проектирования

| Паттерн | Где применяется | Зачем |
|---------|-----------------|-------|
| **Repository** | Слой Data | Абстракция над EF Core, упрощает тестирование |
| **Unit of Work** | Слой Data | Единая транзакция для нескольких репозиториев |
| **Facade** | Слой Services | Упрощение работы с несколькими репозиториями |
| **Dependency Injection** | Везде | Слабая связанность (встроено в ASP.NET Core) |

**Минимум по методичке — 2 паттерна.** Мы используем 4, что выгодно отличает проект.

## 9. Архитектура приложения

Проект разделён на слои (Layered Architecture):

AviaBooking/
├── src/
│ ├── AviaBooking.Api/ # Web API (Controllers, Middleware, Program.cs)
│ ├── AviaBooking.Core/ # Domain (Entities, Enums, Interfaces)
│ ├── AviaBooking.Data/ # EF Core (DbContext, Repositories, Migrations)
│ ├── AviaBooking.Services/ # Бизнес-логика (Facades, DTOs, Validators)
│ └── AviaBooking.Tests/ # Юнит-тесты (xUnit)
├── docs/ # Документация, диаграммы
└── README.md


**Зависимости между слоями:**

Api → Services → Data → Core


- **Core** — ни от кого не зависит (чистый домен)
- **Data** — зависит от Core
- **Services** — зависит от Core и Data
- **Api** — зависит от Services
- **Tests** — зависит от всех

Это **SOLID** в действии: зависимости направлены внутрь, к домену.
